# 历史代码复盘与优化结论

## 1. 历史方案（`lingxing_sdk`）可复用点
- 优势1：`LingxingAPI` 与 `TokenManager` 结构清晰，职责分离。
- 优势2：`PostgresStorage` 独立，便于在脚本场景快速接入。
- 优势3：示例化程度高，适合快速试跑单接口。

## 2. 现有主服务方案优势
- 优势1：统一网关入口（`/lx_openapi`、`/lx_web`、`/ihr`、`/k3`）。
- 优势2：已有稳定性机制（节流、冷却、重试、缓存兜底）。
- 优势3：生产可观测（`request_id`、耗时、错误日志）。

## 3. 兼容性短板（改造动因）
- 短板1：跨 API 族群返回结构不一致。
- 短板2：缺少统一“兼容性事实源”（接口清单与风险分级）。
- 短板3：新接入方没有低风险的“统一响应协议”开关。

## 4. 本轮已落地优化
- 优化1：新增兼容性盘点脚本 `scripts/export_api_inventory.py`。
- 优化2：生成兼容性台账 `docs/project/API兼容性盘点.md`。
- 优化3：新增元数据接口 `GET /meta/compatibility/routes`。
- 优化4：新增可选兼容响应封装：
  - 请求头：`X-Compat-Envelope: 1`
  - 或查询参数：`_compat_envelope=1`
  - 默认关闭，不影响历史调用方。

## 5. 后续优化建议（下一批）
- 建议1：为 `/ihr/{full_path:path}` 与 `/lx_web/{full_path:path}` 增加目标路径白名单，降低动态转发风险。
- 建议2：建立每个 API 组的最小回归集（成功/限频/超时/参数错误）。
- 建议3：将兼容性盘点脚本纳入发布前检查，确保“新增接口必入台账”。
