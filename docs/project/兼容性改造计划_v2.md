# 兼容性改造计划 v2（历史方案复盘后）

## 一、历史方案复盘结论
- 历史 `lingxing_sdk` 的优势：
  - `TokenManager` 与存储解耦，结构清晰。
  - `PostgresStorage` 单一职责明确，适合复用。
  - SDK 调用路径短，便于嵌入不同任务。
- 当前主服务的优势：
  - 已有网关化入口、日志追踪、稳定性策略（节流/冷却/缓存兜底）。
  - 已完成去 MySQL 关键依赖。
- 当前主服务的缺口：
  - 多API返回协议不一致。
  - 缺少统一兼容性清单与可查询元数据。

## 二、优化策略（分批，不破坏旧调用）
1. 盘点层：
   - 自动提取主服务路由，形成可追踪清单。
2. 能力层：
   - 新增兼容性路由元数据接口，作为联调“事实源”。
3. 协议层：
   - 增加“可选兼容响应封装”，通过参数/请求头启用，不影响存量任务。

## 三、阶段目标
- P0：有清单、有入口、有开关。
- P1：按接口组（领星Web/IHR/K3）逐组升级兼容封装。
- P2：建立回归集，防止历史接口回归。

## 四、验收口径
- 可通过接口直接拿到当前兼容性清单。
- 兼容封装开关开启时，响应统一包含 `code/message/data/request_id/source`。
- 开关关闭时，老接口行为不变。
